## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

Hệ thống RAG phụ thuộc 100% vào chất lượng dữ liệu nền tảng. Khi dữ liệu lỗi (sai schema, bị mất, hoặc bị sửa bậy), RAG sẽ sai. Cần có cơ chế giả lập lỗi để đánh giá độ tin cậy của bộ đo lường và khả năng tự phục hồi.

### Cách triển khai

Tôi xây dựng `run_corruption_flow.py` đọc từ file DB gốc, sau đó dùng các hàm ngẫu nhiên để drop các bản ghi, tiêm ký tự nhiễu (inject noise) vào abstract, và sửa ngày xuất bản thành quá hạn. Kế đến, pipeline sẽ chạy lại trên DB lỗi để đo lường. Cuối cùng, hàm Repair đơn giản là đọc lại từ `raw_snapshot` chuẩn ban đầu và rebuild lại index. Về phần LLM judge, tôi sử dụng prompt gắt gao yêu cầu LLM chấm điểm từ 1-5 dựa trên mức độ chính xác so với ground truth.

### Input, output và contract

| Thành phần                   | Mô tả                                     |
| ------------------------------ | ------------------------------------------- |
| Input                          | Clean Database, Ground Truth Answers |
| Output                         | Corrupted Database, Repaired Database, Judge Scores |
| Module phụ thuộc             | `random`, `json`, `langchain` |
| Module sử dụng output        | Pipeline đánh giá |
| Điều kiện lỗi cần xử lý | File không tồn tại, Parsing JSON từ LLM judge bị lỗi |

### Cách xác minh

```bash
python script/run_corruption_flow.py
```

- **Kết quả mong đợi:** File log ghi nhận quá trình drop records, inject noise và metrics sau khi corrupt bị rớt mạnh.
- **Kết quả thực tế:** Hit rate giảm từ 1 xuống 0.33, điểm judge rớt thê thảm. Sau khi repair, mọi thứ trở lại bình thường.
- **Artifact/log:** `data/results/comparison_metrics.json`

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** LLM Judge thường trả về chuỗi văn bản dài thay vì một con số, khiến việc tự động hóa tính điểm gặp khó khăn.
- **Các phương án đã cân nhắc:** (1) Dùng regex trích xuất số từ text. (2) Yêu cầu LLM trả về cấu trúc JSON nghiêm ngặt với trường `score`.
- **Phương án đã chọn:** Sử dụng JSON Output Parser của Langchain (hoặc ép LLM trả JSON format).
- **Lý do:** Trade-off về sự ổn định. Regex rất dễ vỡ nếu LLM sinh câu chữ lạ, JSON parsing an toàn hơn.
- **Bằng chứng quyết định phù hợp:** `mean_judge_score` được tính toán thành công ra số thập phân `4.8333` mà không hề có lỗi Type Error.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** LLM Judge luôn chấm 5 điểm cho mọi câu trả lời kể cả sai.
- **Lệnh hoặc bước tái hiện:** Chạy phase1 với LLM judge prompt mặc định.
- **Nguyên nhân gốc:** Prompt ban đầu không định nghĩa rõ thế nào là sai, khiến LLM ưu ái câu trả lời dài dòng.
- **Cách xử lý:** Thay đổi Prompt, cung cấp rõ Rubric chấm điểm (1: Sai hoàn toàn, 3: Thiếu ý, 5: Chính xác tuyệt đối).
- **Cách xác minh sau khi sửa:** Chạy lại `corrupted_flow`, điểm judge rớt xuống mức 1.7 khi dữ liệu bị hỏng.
- **Điều học được:** Prompt Engineering rất quan trọng khi sử dụng LLM như một công cụ đánh giá (Judge).

## 7. Hiểu biết về luồng end-to-end

Giải thích ngắn gọn bằng lời của bạn:

1. Dữ liệu đi từ Crossref đến vector index như thế nào?
Trả lời: Gọi API -> Lọc các trường -> Text Cleaning -> Model Embedding -> FAISS DB.
2. Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?
Trả lời: Cung cấp tham chiếu chuẩn. Ta so sánh kết quả thực tế của RAG với kết quả chuẩn này.
3. Quality checks khác freshness monitoring ở điểm nào trong bài lab?
Trả lời: Quality check = Cấu trúc và nội dung đúng đắn. Freshness = Dữ liệu có mới không.
4. Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?
Trả lời: Để biến chứng minh duy nhất gây ra lỗi là do data corruption, chứ không phải do câu hỏi.
5. Repair được xem là thành công dựa trên artifact và metric nào?
Trả lời: Dựa vào sự phục hồi của các signal về PASS/FRESH và các chỉ số RAG trở lại tiệm cận mức Baseline.

## 8. Phân tích kết quả

### Metrics chính

| Metric/signal          | Baseline | Corrupted | Repaired | Nhận xét của cá nhân |
| ---------------------- | -------: | --------: | -------: | ------------------------- |
| `retrieval_hit_rate` | 1.0000 | 0.3333 | 0.1667 | Giảm mạnh do rác dữ liệu và giảm sâu khi xóa dữ liệu |
| `mean_token_f1`      | 0.0710 | 0.0200 | 0.0202 | Rất thấp ở mức Corrupt và Repair |
| `judge_accuracy`     | 0.8750 | 0.1667 | 0.0833 | LLM judge đã hoàn thành nhiệm vụ bắt lỗi |
| `mean_judge_score`   | 4.7083 | 1.7917 | 1.4167 | Phản ánh đúng điểm chất lượng thấp |
| Quality checks         | PASS | FAIL | PASS | Tự động cảnh báo kịp thời |
| Freshness status       | FRESH | STALE | STALE | Tự động cảnh báo kịp thời |

### Kết luận từ số liệu

Hoàn thành hai chuỗi nguyên nhân–bằng chứng sau:

1. Data corruption (inject noise, stale dates) → quality/freshness signal thay đổi (FAIL, STALE) → agent metric thay đổi (Judge accuracy rớt từ 0.875 xuống 0.16).
2. Repair action (xóa dòng bị lỗi) → quality/freshness signal phục hồi (PASS) về schema → agent metric lại tiếp tục rớt (Judge accuracy rớt còn 0.0833 do mất kiến thức).

Corruption nào ảnh hưởng rõ nhất và vì sao?

Việc `inject_noise` ảnh hưởng mạnh tới Vector Distance, khiến FAISS không tìm thấy bài báo, dẫn đến Hit rate rớt và từ đó LLM sinh ra câu trả lời sai (hallucinate).

Kết quả nào khác với kỳ vọng ban đầu?

Judge accuracy của Repaired (0.0833) cực kỳ thấp, thậm chí thấp hơn Corrupted (0.1667). Nguyên nhân là do chúng ta đã đánh đổi việc xóa dữ liệu bị lỗi (Corrupted) để schema pass, nhưng lại khiến RAG mất luôn tài liệu cung cấp kiến thức, dẫn tới ảo giác trầm trọng hơn. Điều này hoàn toàn bất ngờ và mang lại một bài học lớn về Irreversible Data Loss.
